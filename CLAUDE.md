# RedLine - working notes for agents

Two GenLayer Intelligent Contracts: a **treasury** that holds prepays and runs
every clock, and a **watcher** that fetches a vendor's terms page and asks a
jury whether a pinned right was cut. Read `docs/ARCHITECTURE.md` first.

## Layout

- `contracts/redline_text.py`, `redline_core.py`, `redline_prompts.py` - pure
  Python, no `gl.*`, tested directly.
- `contracts/treasury_shell.py`, `watcher_shell.py` - the contract classes.
- `contracts/build/` - GENERATED by `python3 deploy/build_contract.py`. Never
  edit by hand; commit it (it is the deployed artifact).
- `tests/direct/` - the suite; `genvm_stub.py` runs the built contracts.
- `deploy/` - `deploy.mjs`, `scenario.mjs`, `probes/`; records `*.json`.
- `examples/` - the fictional vendor's terms pages (`make_pages.py`).
- `frontend/` - the web app; `npm run build` and `npm run e2e` (Studio).

## Commands

```bash
python3 deploy/build_contract.py      # after any change under contracts/
python3 -m pytest tests/direct -q     # must stay green
python3 tests/mutation_check.py       # every mutant must be killed
cd deploy && npm install              # once
REDLINE_KEYS=<dir with principal.key agent.key vendor.key> node deploy.mjs studio
REDLINE_KEYS=... LIVE_CLONE=<clone of the live branch> node scenario.mjs studio
# resumable: run it again after any stop and it carries on (RESET=1 starts over)
REDLINE_KEYS=... node verify.mjs studio   # exact on-chain check of every cover
node verify_code.mjs <commit> scenario-studio.json   # code on chain == build at commit
# networks: studio (SDK 1), studionext and bradbury (SDK 2, fees on every write)
```

## Hard rules (each learned on chain)

- The GenVM version line (`# v0.2.0`) is line 1 and the runner header line 2,
  followed immediately by code. Studio Next refuses a contract without the
  version line.
- The web fetch is written inline in both the leader and validator closure.
- Closures capture plain Python values only.
- A payable method never raises after value has arrived: refuse and credit.
- The treasury never reads the watcher; reports arrive as messages only the
  watcher may send.
- Keep each deployed file under about 19 KB (Bradbury's gas cap);
  `test_it_fits_bradburys_gas_cap` enforces it.
- Never commit keys. Never put a model identifier in the repository.
- The watcher is within about 75 bytes of the gas cap: new watcher logic
  must pay for itself in bytes.
- The `live` branch holds only test pages edited by `scenario.mjs`; never
  merge it, never build it. Vercel builds `main`.
- After a run, `node verify.mjs <net>` then `python3 deploy/readme_record.py`
  so the README shows the deployed contracts and their records.

## Releases and milestones in the README

- Never replace a submitted release's contract addresses. Each release or

  contracts"; each milestone in its own section, as Remit does), with

## RedLine on PayPal (branch `paypal`)

A second product on the same core, for the PayPal AI Hackathon (deadline
12 Nov 2026, 12:00 PST). Read `docs/PAYPAL-ARCHITECTURE.md` before writing
code; `docs/PAYPAL-PLAN.md` is the product and schedule, `docs/PAYPAL-RULES.md`
the rules.

- All new code is under `paypal/`. `contracts/redline_core.py`,
  `redline_text.py` and `redline_prompts.py` are imported **unchanged**; the
  GenLayer shells and `contracts/build/` are not touched on this branch.
- Money: a PayPal **authorization** is the hold. Settlement is
  `capture(share)` then `void(rest)`, planned from `redline_core.close` and
  executed through the `paypal_ops` journal with deterministic
  `PayPal-Request-Id`s. Never compute a share outside `redline_core`; never
  retry a PayPal write without reconciling from PayPal's record first.
- The stored `covers.core` dict is the only truth for a cover's state and
  money; columns beside it are for queries and are rewritten from it.
- A breach is **confirmed by a second check before `apply_check` hears of
  it** (the core lets a reported breach stand). The panel fails closed toward
  the vendor: errors, splits and `cannot_tell` never make a breach.
- Reauthorize only at settlement, when a capture is due and the current
  authorization's 3-day honor period is over; capture and void the new id.
- Checkout is journaled too: an authorization whose cover was never saved is
  voided by the sweep. Every authorization ends settled or voided.
- Never store, log or anchor PayPal's response bodies (they carry the payer's
  name and email): ids, statuses, amounts, error name and debug id only.
- Contested panel readings never cut a cover; a breach always needs the
  confirming check ("check now" may run it at once in the demo).
- Build order: the sandbox spike (authorize, partial capture, void, sums read
  back from PayPal) before anything else.
- Every PayPal call goes to the sandbox; the client refuses live hosts.
- Fetching pages: only allowed hosts, no private addresses, size and time
  limits (architecture section 9.1).
- Demo covers are checked only in-process; GitHub Actions checks long covers
  and settles. Never fetch a demo page from the scheduled worker.
- Still: no keys and no model identifiers in the repository.
